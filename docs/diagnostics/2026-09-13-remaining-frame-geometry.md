## Grown minibuffer and frame height

GNU `frame-height` reads the `height` entry of `frame-parameters`. Once native changes have settled, that entry and `frame-text-lines` both report `FRAME_LINES`. During pending native changes, `frame-parameters` has a deliberately different compatibility path, so comparisons must wait for settled geometry. Sources: [frame.el:1883](/home/exec/Projects/github.com/emacs-mirror/emacs/lisp/frame.el:1883), [frame.c:4134](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:4134), [frame.c:4454](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:4454).

Growing the minibuffer redistributes existing inner height between the root and minibuffer; it does not subtract the extra minibuffer rows from the frame's text area. GNU's adjustment code obtains the old inner height from the root window plus the actual minibuffer height. See [adjust_frame_size](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:840).

Concrete Neomacs candidate: the GUI branch of `Frame::resize_pixelwise` derives lines from root-window height and adds `i64::from(minibuffer_leaf.is_some())`. This counts every minibuffer as one row even when it is larger. Meanwhile the public GUI `frame-text-lines` derives its result from native text pixels. This explains the recorded mismatch without blaming font discovery. See [window/mod.rs:4731](../../crates/neovm-core/src/window/mod.rs) and [frame/mod.rs:521](../../crates/neovm-core/src/emacs_core/display/frame/mod.rs).

Candidate public oracle:

1. Disable menu/tool bars, settle an 80×24 text grid, and record native/text height and both line queries.
2. Grow the minibuffer to at least three rows using the existing public minibuffer/echo-area flow. Record `window-pixel-height` for both root and minibuffer to prove it grew.
3. Trigger a width-only resize while the minibuffer remains grown; wait for geometry/native presentation. Assert unchanged native/text height and matching settled `frame-height`/`frame-text-lines` at 24.
4. Apply a live font change, then verify the entire 24-row text grid, including the minibuffer, rather than asserting the root alone has 24 rows.

A deterministic core control can grow the minibuffer through the existing `grow_mini_window_with_max_lines` abstraction before applying a native resize. Do not add another echo-height calculator or reset the minibuffer to hide the bug. Reuse `frame_text_height_pixels`, current actual minibuffer bounds, and `sync_window_area_bounds`. Keep terminal/batch accounting separate: existing non-GUI conventions and tests are not evidence that the GUI branch should add a boolean minibuffer count.

## Child initial width with chrome

GNU's text/native conversion adds scrollbar area, both fringes, and twice the internal border to text width. The reverse subtracts exactly those components. This applies to child-frame text sizing too; a parent relationship does not change the meaning of an integer `width` frame parameter. See [frame.h:1788](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.h:1788) and the initial/explicit resize use of [adjust_frame_size](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:775).

The tracked `desktop-font-live-child` fixture now disables fringes, scrollbars and border. That is a valid no-chrome live-font control, but cannot establish initial chrome conversion. The older `live-child.log` and `live-child-diagnostic.log` under `target/diagnostics/issue-360/startup-fonts/` record failure before the live update; the plan explicitly leaves this gap open.

Primary candidate: `x_create_frame_impl` computes initial width from parsed width × inherited cell width plus borders, before installing default/explicit fringe and scrollbar parameters. It does not add those horizontal non-text areas to the allocation. The later public text-width getter subtracts them, producing too few columns. A secondary path, `set_frame_text_size`, directly writes a child's width as columns × cell width; its handling of chrome should be reviewed under the same invariant. Sources: [window_cmds/mod.rs:6809](../../crates/neovm-core/src/emacs_core/display/window_cmds/mod.rs), [window_cmds/mod.rs:5340](../../crates/neovm-core/src/emacs_core/display/window_cmds/mod.rs).

Candidate oracle: create a 40×10 child with the known Ubuntu Mono 9×18 font, explicit nonzero left/right fringes and border, then separately enable a scrollbar with explicit width. Assert text width 360 and native width equal to 360 plus the **observed** fringe/scrollbar/border contribution. Repeat with a different explicit child font from the parent. This catches both missing chrome and inherited-metrics ordering. Apply the live font update only after startup invariants pass; expect text width 520 at the new 13-pixel cell. Do not encode a guessed toolkit scrollbar width.

Reuse `FrameResizeRequest::TextPixels`, `frame_non_text_total_width_pixels_in_state`, `frame_text_width_pixels_in_state`, `Frame::horizontal_non_text_width`, and the existing opened-font realization. Construct/install effective parameters and font before converting the requested text grid to allocation. Preserve the current local child resize path; a child should not accidentally be sent through top-level host-window creation. Existing pixelwise child border tests near [window_cmds/tests/mod.rs:8700](../../crates/neovm-core/src/emacs_core/display/window_cmds/tests/mod.rs) should remain controls against adding the border twice.

## Font changes and split-window minimum overrides

GNU uses inhibit mode 3 for font changes. It suppresses an axis only when the current inner size is at least that axis's window-tree minimum **and** policy otherwise inhibits resizing. If a larger font makes existing split windows too small, the minimum overrides `frame-inhibit-implied-resize` on that axis. This is not equivalent to unconditional preservation of allocated pixels. See [frame.c:775](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:775) and [frame.c:884](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:884).

GNU first checks integer `min-width`/`min-height` frame parameters: those override the dynamic tree minimum and are converted from cells using the current default font. Otherwise it calls the Lisp `frame-windows-min-size` in pixel units. That function adds minibuffer height vertically and delegates tree recursion to `window-min-size`: sum on the split axis, maximum on the perpendicular axis, accounting for fixed-size windows, safe minima, fringes, margins, scrollbars and dividers. Sources: [frame.c:506](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:506), [window.el:1605](/home/exec/Projects/github.com/emacs-mirror/emacs/lisp/window.el:1605), [window.el:1899](/home/exec/Projects/github.com/emacs-mirror/emacs/lisp/window.el:1899).

Neomacs `FontChangeGeometryPolicy::for_live_frame` currently checks inhibition/fullscreen/TTY state without the minimum comparison. Reuse the loaded GNU Lisp minimum functions; do not create another recursive Rust window-minimum algorithm. The native `frame-windows-min-size` subr returning zero is intentional in **both** engines and is overridden by `window.el`. A bare-core test that only sees that placeholder cannot establish real split-window behavior. See [font/mod.rs:479](../../crates/neovm-core/src/emacs_core/display/font/mod.rs), [stubs.rs:1553](../../crates/neovm-core/src/emacs_core/lisp/native/builtins/stubs.rs), and [the shadowing contract tests](../../crates/neovm-core/src/emacs_core/lisp/native/builtins/tests/rust_subrs_shadowed_by_lisp.rs).

Candidate oracle: create two side-by-side windows at a sufficiently small initial font/frame width, set an explicit `window-min-width`, settle, then enable inhibition and enlarge the font until the pixel minimum exceeds old inner width. Record the public `frame-windows-min-size` results after the new font is installed. Expect native width to grow enough to satisfy that minimum; an unaffected vertical axis stays fixed. Use a stacked split for the vertical counterpart. Include controls where the old allocation still satisfies minima, and where explicit frame `min-width` overrides the tree calculation. Start outside fullscreen: a window manager can refuse external requests, so fullscreen tests require a separate allocation-versus-request assertion.

GNU computes minimum width/height after font/chrome facts change, but retains old root/minibuffer geometry for comparison. Preserve that ordering when extending the existing opened-font sync and frame-resize path. Keep frame geometry hints distinct from this evaluator/Lisp minimum computation; their current base-size minimum is not the dynamic split-tree minimum.

## Overlapping resize requests and native observations

GNU explicitly distinguishes requested dimensions from confirmed native size via `new_size_p`; `do_pending_window_change` does not apply a request before the window manager honors it. Delayed observations replace stored observed dimensions, and actual change processing clears the pending slots before internal mode-5 adjustment. GNU itself documents a controversial reset that can drop an earlier request when the window manager rejects a later one. There is no general GNU guarantee that every issued request receives a uniquely identifiable acknowledgment. Sources: [frame.c:975](/home/exec/Projects/github.com/emacs-mirror/emacs/src/frame.c:975), [dispnew.c:6665](/home/exec/Projects/github.com/emacs-mirror/emacs/src/dispnew.c:6665), [dispnew.c:6696](/home/exec/Projects/github.com/emacs-mirror/emacs/src/dispnew.c:6696).

Neomacs has one `PendingGuiResize` containing requested rows/columns and a sent flag. Each Resize input installs native scale and dimensions through `resize_pixelwise_with_buffer_constraints`; `resize_pixelwise` clears that pending intent. Font changes preserve a pending grid if one exists, but an earlier native observation can clear a later request's grid. Also inspect `flush_pending_live_gui_resize`, which takes the pending object even when its host request was already sent. Sources: [window/mod.rs:3197](../../crates/neovm-core/src/window/mod.rs), [keyboard.rs:2688](../../crates/neovm-core/src/keyboard.rs), [font/mod.rs:523](../../crates/neovm-core/src/emacs_core/display/font/mod.rs), [window_cmds/mod.rs:5578](../../crates/neovm-core/src/emacs_core/display/window_cmds/mod.rs).

Candidate deterministic seam: use `RecordingDisplayHost` and public Lisp font/size calls, as the existing [frame_resize_test.rs](../../crates/neovm-core/src/emacs_core/display/window_cmds/tests/frame_resize_test.rs) does. Issue A then B before either observation, deliver A, then issue a third font/size change and verify the intended grid was not recomputed from A's allocation divided by B's metrics. Deliver B and a repeated B, and assert final native geometry reflects actual observations while newer unsent intent still reaches the host. Include rejection at the original allocation and interleaved focus/key input; existing tests already cover isolated rejection, duplicate completion, and one unsent-request preservation case.

**Do not infer staleness from dimensions alone.** Resize input carries frame identity, dimensions and scale, but no native request token. An A-sized notification after requesting B can still describe the current real allocation. Dropping it merely because it differs from B would make Lisp geometry disagree with the compositor. Likewise a presentation submission number is not a native resize-request acknowledgment. A fix should separate observed allocation from outstanding intent in the existing frame lifecycle, or establish a real native correlation contract before adding acknowledgment IDs.

A public GNU/Neomacs GUI stress sequence can issue several sizes/font changes in one callback and assert final settled geometry; it does not deterministically control compositor acknowledgment order. Pair that end-to-end check with the existing host/event seam, and describe the latter as deterministic Neomacs lifecycle coverage rather than fabricated GNU protocol evidence.
